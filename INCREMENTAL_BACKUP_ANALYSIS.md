# Анализ возможностей реализации Diff и Incremental бэкапов для PostgreSQL

## 📋 Обзор

Текущая реализация использует `pg_dump` для создания **полных (full)** логических бэкапов PostgreSQL. В этом документе анализируются возможности добавления **дифференциальных (diff)** и **инкрементальных (incremental)** бэкапов.

---

## 🔍 Текущая реализация

### Используемый подход
- **Инструмент:** `pg_dump` / `pg_restore`
- **Тип бэкапов:** Полные логические бэкапы
- **Форматы:** Custom (-Fc) и Plain SQL (-Fp)
- **Особенности:** 
  - Сжатие gzip
  - Исключение системных схем
  - Поддержка удаленного хранилища

### Ограничения pg_dump
❌ `pg_dump` **не поддерживает** нативно:
- Инкрементальные бэкапы
- Дифференциальные бэкапы
- Бэкапы только измененных таблиц (без дополнительной реализации)

---

## 💡 Возможные подходы к реализации

### 1. Point-in-Time Recovery (PITR) с WAL архивированием ⭐⭐⭐⭐⭐

**Описание:**
- Использование `pg_basebackup` для базовых физических бэкапов
- Непрерывное архивирование WAL (Write-Ahead Log) файлов
- Восстановление до любой точки времени

**Преимущества:**
- ✅ Нативная поддержка PostgreSQL
- ✅ Минимальный размер инкрементальных данных (только WAL)
- ✅ Восстановление до любой точки времени
- ✅ Очень быстрые бэкапы

**Недостатки:**
- ❌ Требует настройки PostgreSQL (wal_level, archive_mode)
- ❌ Физические бэкапы (не переносимы между версиями)
- ❌ Требует доступ к серверу БД (не через pg_dump)
- ❌ Нужны права superuser для настройки

**Требования:**
```postgresql
-- В postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'cp %p /path/to/wal_archive/%f'
```

**Сложность реализации:** Высокая
**Рекомендация:** Отдельный модуль для PITR, опциональная функция

---

### 2. Логические инкрементальные бэкапы на основе метаданных ⭐⭐⭐⭐

**Описание:**
- Хранение метаданных о последнем бэкапе (размеры таблиц, количество строк, checksums)
- Сравнение текущего состояния с метаданными
- Бэкап только измененных таблиц
- Объединение при восстановлении

**Преимущества:**
- ✅ Работает с текущей архитектурой (pg_dump)
- ✅ Логические бэкапы (переносимы)
- ✅ Не требует изменений в PostgreSQL
- ✅ Может работать без superuser прав

**Недостатки:**
- ❌ Сложная логика отслеживания изменений
- ❌ Нужно хранить метаданные о предыдущих бэкапах
- ❌ Восстановление требует полного + все инкрементальные бэкапы
- ❌ Не учитывает изменения схемы автоматически

**Реализация:**
```python
# Псевдокод подхода
1. Получить метаданные текущих таблиц:
   - pg_stat_user_tables (n_tup_ins, n_tup_upd, n_tup_del)
   - pg_total_relation_size()
   - pg_stat_user_tables.last_vacuum, last_autovacuum

2. Сравнить с сохраненными метаданными последнего бэкапа

3. Для измененных таблиц:
   pg_dump -t schema.table --data-only ...

4. Сохранить метаданные для следующего бэкапа
```

**Сложность реализации:** Средняя
**Рекомендация:** Хороший компромисс для текущей архитектуры

### 3. Использование специализированных инструментов ⭐⭐⭐

**Инструменты:**
- **pg_probackup** (Postgres Pro) - бесплатный, открытый
- **pgBackRest** - открытый, популярный
- **Barman** (2ndQuadrant) - открытый

**Преимущества:**
- ✅ Профессиональные решения
- ✅ Полная поддержка инкрементальных бэкапов
- ✅ Компрессия, шифрование, параллельная обработка
- ✅ Хорошая документация

**Недостатки:**
- ❌ Дополнительная зависимость
- ❌ Могут требовать специальной настройки PostgreSQL
- ❌ Интеграция в существующий код
- ❌ Для pg_probackup нужна специальная сборка PostgreSQL

**Сложность интеграции:** Средняя-Высокая
**Рекомендация:** Рассмотреть как альтернативу, но сложнее интегрировать

### 4. Логическая репликация для инкрементальных изменений ⭐⭐

**Описание:**
- Настройка логической репликации PostgreSQL
- Сохранение изменений из репликационного слота
- Восстановление через применение изменений

**Преимущества:**
- ✅ Реал-тайм отслеживание изменений
- ✅ Минимальная нагрузка на основную БД

**Недостатки:**
- ❌ Очень сложная настройка
- ❌ Требует изменения конфигурации PostgreSQL
- ❌ Нужен отдельный сервер для репликации
- ❌ Высокая сложность восстановления

**Сложность реализации:** Очень высокая
**Рекомендация:** Не рекомендуется для текущего проекта

## 🎯 Рекомендуемый подход: Метаданные-основанные инкрементальные бэкапы

### Архитектура решения

```
┌─────────────────────────────────────────┐
│   Metadata Storage (JSON/YAML)         │
│   - Last backup timestamp              │
│   - Table sizes                        │
│   - Row counts                         │
│   - Statistics (n_tup_ins/upd/del)     │
└─────────────────────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│   Change Detection                     │
│   - Compare current vs saved metadata  │
│   - Identify changed tables            │
└─────────────────────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│   Selective Backup                     │
│   - Full: All tables                   │
│   - Diff: Changed tables only          │
│   - Inc: Changes since last backup     │
└─────────────────────────────────────────┘
```

### Типы бэкапов

#### Full Backup (полный)
- Как сейчас - все таблицы
- Формат: `database_YYYYMMDD_HHMMSS_full.dump`

#### Differential Backup (дифференциальный)
- Все изменения с момента последнего полного бэкапа
- Формат: `database_YYYYMMDD_HHMMSS_diff.dump`
- Размер: средний

#### Incremental Backup (инкрементальный)
- Только изменения с момента последнего бэкапа (любого типа)
- Формат: `database_YYYYMMDD_HHMMSS_inc.dump`
- Размер: минимальный

### Алгоритм работы

```python
def create_incremental_backup(database, backup_type='auto'):
    """
    Создает инкрементальный/дифференциальный бэкап
    
    Args:
        backup_type: 'full', 'diff', 'inc', 'auto'
        - 'auto': автоматически определяет тип
        - 'full': всегда полный
        - 'diff': дифференциальный (от последнего full)
        - 'inc': инкрементальный (от последнего любого)
    """
    
    # 1. Получить метаданные текущего состояния
    current_metadata = get_database_metadata(database)
    
    # 2. Загрузить метаданные последних бэкапов
    last_metadata = load_backup_metadata(database)
    
    # 3. Определить измененные таблицы
    if backup_type == 'auto':
        backup_type = determine_backup_type(last_metadata)
    
    changed_tables = compare_metadata(current_metadata, last_metadata)
    
    # 4. Создать бэкап
    if backup_type == 'full' or not changed_tables:
        # Полный бэкап всех таблиц
        create_full_backup(database)
    else:
        # Инкрементальный/дифференциальный - только измененные
        for table in changed_tables:
            create_table_backup(database, table)
    
    # 5. Сохранить новые метаданные
    save_backup_metadata(database, current_metadata, backup_type)
```

### SQL запросы для метаданных

```sql
-- Получение метаданных о таблицах
SELECT 
    schemaname,
    tablename,
    pg_total_relation_size(schemaname||'.'||tablename) as total_size,
    pg_relation_size(schemaname||'.'||tablename) as table_size,
    n_live_tup as row_count,
    n_tup_ins as inserts_since_vacuum,
    n_tup_upd as updates_since_vacuum,
    n_tup_del as deletes_since_vacuum,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY schemaname, tablename;

-- Проверка изменений схемы
SELECT 
    schemaname,
    tablename,
    pg_get_userbyid(tableowner) as owner,
    hasindexes,
    hasrules,
    hastriggers
FROM pg_tables
WHERE schemaname NOT IN ('information_schema', 'pg_catalog');
```

## ⚠️ Ограничения и предупреждения

### Ограничения метаданных-подхода:
1. **Изменения схемы** не отслеживаются автоматически
   - Решение: периодические полные бэкапы

2. **Точность** зависит от статистики PostgreSQL
   - Решение: использовать несколько индикаторов

3. **Восстановление** требует полного + цепочки инкрементальных
   - Решение: автоматическое объединение при восстановлении

4. **Производительность** при проверке метаданных
   - Решение: кэширование и оптимизация запросов

### Требования к PostgreSQL:
- Доступ к `pg_stat_user_tables` (обычно есть)
- Периодическая статистика (ANALYZE)
- Версия 9.6+ (для некоторых функций)

## 📈 Ожидаемые преимущества

### Экономия места:
- **Полные бэкапы:** ~100% данных каждый раз
- **Дифференциальные:** ~20-40% данных (если изменено 20-40%)
- **Инкрементальные:** ~5-15% данных (если изменено 5-15%)

### Экономия времени:
- **Полный бэкап:** 100% времени
- **Дифференциальный:** 30-50% времени
- **Инкрементальный:** 10-30% времени

### Пример для БД 100GB:
- **Полный бэкап:** 100GB, 2 часа
- **Дифференциальный:** ~30GB, 45 минут (если изменено 30%)
- **Инкрементальный:** ~10GB, 20 минут (если изменено 10%)
